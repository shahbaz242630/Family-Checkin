# Backend robustness review (NestJS + Prisma) — 2026-09-05

Scope: `apps/backend/src`, `prisma/schema.prisma`, RLS SQL, `scripts/run-operations-check-ins.ts`, `.github/workflows/operations-check-ins.yml`. Read-only. Paths are relative to `apps/backend/` unless prefixed. Every finding has a concrete scenario; anything I could not execute is marked "unverified".

## Executive summary

**Verdict: not production-ready.** The safety loop (send check-in -> detect silence -> alert family) has three defects that break it outright, and the input/concurrency/observability layer is thin enough that one bad row or one slow Twilio call takes the whole scheduler down silently.

Counts: **Blocker 3 · High 10 · Medium 13 · Low 10** (36 findings).

Top 10 fixes, in order:
1. Remove `POST /receiver-replies/fake` from the production module (or register it only when `CHANNEL_PROVIDER_MODE=fake` and require the cron secret). [B1]
2. Fix the audit PII guard: `backupContactId` matches `/contact/i`, so every backup-contact alert throws after the SMS is sent and the check-in never becomes ESCALATED. Add a test that drives escalation through the real `AuditService`. [B2]
3. Validate `timezone` and `scheduleTimeWindow` on receiver create/update, and make the due-receiver filter skip a bad row instead of throwing for everyone. [B3]
4. Escalate when the cascade is exhausted (`markCheckInNeedsAttention` only audits today) or wire `escalateOverdueCheckIns` into the runner. [H3]
5. Stop trusting `user_metadata.phone`; freeze the sender phone after first sync; refuse requests from soft-deleted users; delete/ban the Supabase auth user on account deletion. [H1, H2]
6. Make cron sends idempotent: status-conditioned `updateMany` claims, `pg_advisory_xact_lock` per run, unique index on (receiverId, local date). [H4]
7. Dedupe daily check-ins on the receiver's local calendar date, not the UTC day. [H5]
8. Webhooks: 200 + audit on unknown replies, dedupe by `MessageSid`, answer Twilio voice action URLs with TwiML. [H7]
9. `AbortSignal.timeout` on every fetch, try/catch per receiver in `sendDueCheckIns`, a structured `Logger` in every catch, surface Twilio error codes. [H8, H9]
10. Zod schemas on every `@Body()` and status-guarded transitions wherever a check-in/attempt status is written. [M1, M4]

## Tests: risky paths with no coverage

- Escalation, reply handling and check-in services are tested only with `InMemoryAuditService` (`escalations.service.spec.ts:57`, `receiver-reply.service.spec.ts:466`, `check-ins.service.spec.ts:270`); the real `AuditService` guard is never exercised end-to-end, which is why B2 ships green.
- No spec at all for: `twilio-rendering.ts`, `twilio-http-client.ts`, `expo-push.gateway.ts`, `prisma-account.repository.ts` (deletion transaction, `consumeStepUpToken`), `prisma-users.repository.ts`, `prisma-notifications.repository.ts`, `main.ts`.
- Timezone: one `Asia/Dubai` case (`prisma-check-ins.repository.spec.ts:16-73`); nothing for a UTC-midnight straddle, DST, an invalid tz, or a malformed window.
- No concurrency tests anywhere (grep `concurrent|parallel|race`: none).
- `escalateOverdueCheckIns` is tested (`check-ins.service.spec.ts:463`) but has no production caller; no test asserts what `runCheckIns` actually wires.
- The webhook spec never sends an unsupported reply, a duplicate `MessageSid`, or a non-E.164 `From`.
- No test that `POST /receiver-replies/fake` is absent in configured mode.

## Already solid (do not redo)

- Cron secret and Twilio HMAC checks are timing-safe and fail closed when the secret/base URL is unset (`operations.controller.ts:86-103`, `provider-webhooks.controller.ts:324-351`).
- Object-level authorisation is enforced in the app on every read/write (`userId` in every `where`; backup contacts verify receiver ownership; admin roles per route); it does not rely on RLS through the service connection.
- Step-up design: hashed OTP and token, 10-minute TTLs, 5-attempt lock, single-use, action-bound.
- Env validated with zod at boot, KMS key length checked, no `process.env` reads outside config (scheduler script excepted by design).
- AES-256-GCM with a fresh IV per value; email/phone/name/notes/transcripts/report content encrypted; an audit-metadata PII guard exists (over-eager, but the intent is right); the audit table has no-update/no-delete triggers.
- RevenueCat idempotency via `idempotency_keys` PK + P2002 handling; subscription upsert keyed by external id.
- Account deletion is a single transaction that anonymises user, receivers and backup contacts.
- Helmet, global throttler, CORS allow-list, configurable `trust proxy`; webhooks/cron opt out of throttling explicitly.
- Scheduler script exits non-zero on non-2xx; the workflow has a concurrency group and job timeout.
