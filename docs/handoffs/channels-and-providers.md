## What it does

- Every outbound message and call goes through one vendor-neutral `ChannelProvider` (`sendMessage`, `makeVoiceCall`, `isAvailableForNumber`) per `Channel` (`WHATSAPP`, `SMS`, `VOICE`), so cascade, consent and escalation logic never names a vendor.
- `CHANNEL_PROVIDER_MODE` decides the implementations at boot: `fake` yields three `FakeChannelProvider`s that record sends in memory; `configured` yields the Twilio-backed `WhatsappProvider`, `SmsProvider` and `VoiceProvider`.
- `MessageCatalogService` turns a template key + language + variables into the text a person reads: an active `channel_templates` row wins (seeded for en, ar, es, hi, ur, ml, ta, bn on SMS and WhatsApp), then in-code English copy, then English with `fallback: true`; a missing or blank required variable throws.
- `ChannelRouterService` dispatches by channel and resolves a reachable plan for a phone number (`PRIMARY_AVAILABLE` / `FALLBACK_SELECTED` / `MANUAL_REQUIRED`); the tech profile decides the cascade shape upstream in `CheckInsService`.
- Signed Twilio webhooks bring inbound replies (SMS/WhatsApp text and quick-reply buttons, voice DTMF/speech), message delivery statuses and call outcomes (status, AMD) back into `ReceiverReplyService` and `CheckInsService`. An `undelivered` or `failed` message fails its attempt within seconds instead of after the response window (CB-016).
- Every provider event with an id is stored once: the natural key `(provider, eventType, providerEventId)` is a primary key in `provider_webhook_event_keys`, claimed with `ON CONFLICT DO NOTHING` in the same transaction as the `provider_webhook_events` row, so a Twilio retry or a duplicate callback answers `processed: 0` and adds nothing (CB-016).
- Receiver-facing copy names the sender: `senderDisplayName` is the sender's stored display name (`users.displayNameEncrypted`, read through `UsersService.senderDisplayNameFor`) and falls back to "your family member" ("their family member" in backup alerts) when none is stored (CB-010).
- In fake mode only, `POST /receiver-replies/fake` drives the real reply pipeline with no provider involved, and `GET /receiver-replies/fake/outbound` lists what the fake providers sent; every fake send also prints a `[fake-provider]` line in the terminal.

## Routes and contracts

- `POST /provider-webhooks/twilio/messaging` — Twilio. `X-Twilio-Signature` (HMAC-SHA1 over `${PUBLIC_API_BASE_URL}` + path + sorted key/value pairs, compared timing-safe). Body `From`, `Body`, `ButtonText`, `ButtonPayload`, `MessageSid`; `ButtonPayload` wins, then `ButtonText`, then `Body`. `whatsapp:` prefix on `From` selects `WHATSAPP`. Replays of a stored `MessageSid` short-circuit to `{ ok: true, processed: 0 }`.
- `POST /provider-webhooks/twilio/messaging/status` — the `StatusCallback` of every SMS and WhatsApp send (CB-016). Signed. Body `MessageSid`, `MessageStatus` (`queued`, `sent`, `delivered`, `read`, `undelivered`, `failed`), `ErrorCode`, `To`, `From`. A missing `MessageSid` or `MessageStatus` is `processed: 0`. Otherwise the event is keyed `messaging_status` / `MessageSid:MessageStatus`: a stored key short-circuits to `processed: 0`; a new one calls `CheckInsService.recordMessagingProviderStatus({ providerMessageId, messageStatus, errorCode })` first (only `undelivered` and `failed` change anything) and stores the event after it succeeded, PII-free (`MessageSid`, `MessageStatus`, `ErrorCode`, `channel`). `processed: 1` only when this request stored the event.
- `POST /provider-webhooks/twilio/voice` — the `<Gather>` action URL. Signed. `Digits` first, then `SpeechResult`; `To` is treated as the receiver's number; `CallSid` becomes the provider message id.
- `POST /provider-webhooks/twilio/voice/status` — `StatusCallback`. Signed. Stores a `voice_status` event (keyed `CallSid:CallStatus`, once) and calls `CheckInsService.recordVoiceProviderFailure({ providerMessageId, providerStatus })`; a replay is `processed: 0` but still runs the guarded transition.
- `POST /provider-webhooks/twilio/voice/amd` — `AsyncAmdStatusCallback`. Signed. Stores a `voice_amd` event (keyed `CallSid:AnsweredBy`, once) and calls `recordVoiceProviderFailure({ providerMessageId, answeredBy })`.
- `POST /provider-webhooks/whatsapp` and `POST /provider-webhooks/sms` — header `x-nearby-webhook-secret` = `CHANNEL_WEBHOOK_SECRET`, timing-safe. Meta-shaped and generic/Twilio-style bodies respectively; neither is wired to a live provider (CB-019, CB-021).
- All webhook routes are `@SkipThrottle()` and answer `{ ok: true, processed: number }` only — never phones, bodies or payloads.
- `POST /receiver-replies/fake` — registered **only** when `channelProviderModeFromEnv() === 'fake'` (`ReceiverRepliesModule.register`); 404 in configured mode. Header `Authorization: Bearer <OPERATIONS_CRON_SECRET>` via `assertBearerSecret`, else 401. Body `{ fromPhone, channel, body, providerMessageId? }`. Returns `{ ok: true, receiverId, action, consentStatus?, checkInId?, checkInStatus?, backupContactId? }`.
- `GET /receiver-replies/fake/outbound?limit=N` — same registration rule and the same cron-secret bearer. Returns `{ ok: true, count, sends[] }`, newest first; `limit` is 1–200 (default 50, 400 otherwise). A record is `kind: "message"` (`to`, `providerMessageId`, `templateKey`, `language`, `fallback`, rendered `body`) or `kind: "voice_call"` (`to`, `providerCallId`, `scriptKey`, `language`, `variables`, `fromNumber?`). Backed by `FakeOutboundRecorder` (200-record ring buffer, one per process), which also prints each record through the Nest logger as `[fake-provider] SMS message to ***3401 (checkin_daily, en) fake-SMS-message-1: "…"`. Configured providers never write to it.

Outbound Twilio shapes (asserted by `configured-channel-providers.spec.ts`): SMS `POST .../Accounts/{Sid}/Messages.json` with `To`/`From`/`Body` (body rendered by the catalog) plus `StatusCallback` when `PUBLIC_API_BASE_URL` is set. WhatsApp the same URL with `whatsapp:`-prefixed `To`/`From`, `ContentSid`, `ContentVariables` (JSON of the variables) and the same optional `StatusCallback` — the SID comes from `TWILIO_WHATSAPP_CONTENT_SIDS` keyed `templateKey:language` then `templateKey`, and a miss throws before any HTTP call. Voice `POST .../Accounts/{Sid}/Calls.json` with inline `Twiml`, `MachineDetection=Enable`, `AsyncAmd=true`, `AsyncAmdStatusCallback`, `AsyncAmdStatusCallbackMethod=POST`, `StatusCallback`, `StatusCallbackEvent='initiated ringing answered completed'`, `StatusCallbackMethod=POST`. The TwiML is two identical `<Gather input="dtmf" numDigits="1" timeout="10" method="POST" action=".../provider-webhooks/twilio/voice">` blocks each wrapping `<Play>${VOICE_AUDIO_BASE_URL}/{en|ar|es|hi|ur}/{scriptKey}.wav</Play>`, then `<Hangup/>`.

`senderDisplayName` is filled the same way by every caller: `UsersService.senderDisplayNameFor(userId, fallback?)` decrypts `users.displayNameEncrypted` (stored by `POST /auth/sync-user` from Supabase `full_name`, see `docs/handoffs/auth-and-accounts.md`) and returns `NEUTRAL_SENDER_DISPLAY_NAME` ("your family member") when the sender has no name; `escalations.service.ts` passes `NEUTRAL_SENDER_DISPLAY_NAME_FOR_BACKUP_CONTACTS` ("their family member") as the fallback. The name is decrypted for the provider call only and never written to an audit row.

Voice uses `scriptKey`, not the catalog: `checkin_daily_voice`, `consent_request_voice`, `receiver_checkins_paused_voice`, `receiver_checkins_ended_voice`, `sender_escalation_siren_voice`.

Languages: `channel_templates` holds every key above for `en`, `ar`, `es`, `hi`, `ur`, `ml`, `ta`, `bn` on `SMS` and `WHATSAPP` (the WhatsApp row is the text to submit as the Content Template; its `externalId` is where the approved Content SID belongs, CB-020). The English rows are identical to `IN_CODE_MESSAGE_TEMPLATES`, which stays as the last-resort fallback. Any other language (`fr`, `tl`, …) falls back to English with `renderFallback: true` in the audit metadata. Every non-English body is a machine translation with `approvedAt` NULL; review status and instructions live in `docs/handoffs/message-copy-review.md`. `{{channelsTried}}` is still filled in English by `describeChannelsTried`.

## How to exercise it locally (fake mode)

- Set `CHANNEL_PROVIDER_MODE=fake` and `OPERATIONS_CRON_SECRET` in `apps/backend/.env` per `docs/EMULATOR_RUNBOOK.md` §3, then start the backend. No `TWILIO_*` value is needed.
- Drive an inbound reply: `POST /receiver-replies/fake` with `Authorization: Bearer <OPERATIONS_CRON_SECRET>` and `{"fromPhone":"+44...","channel":"SMS","body":"YES"}`. Without the bearer it is 401; with `CHANNEL_PROVIDER_MODE=configured` the route is 404.
- Drive an outbound send: `POST /operations/check-ins/run` (cron-secret bearer). The `check_in.sent` audit row carries `renderedLanguage` and `renderFallback`; the rendered body prints in the backend terminal as a `[fake-provider]` line and is returned by `GET /receiver-replies/fake/outbound` (cron-secret bearer).
- Exercise a Twilio route locally by setting `TWILIO_AUTH_TOKEN` and `PUBLIC_API_BASE_URL` to test values and computing the HMAC-SHA1 signature the same way `computeTwilioSignature` does; an unsigned request is 401.
- Delivery status (CB-016): the fake providers never post statuses, so drive `POST /provider-webhooks/twilio/messaging/status` yourself with a signed body whose `MessageSid` is the SENT attempt's `providerMessageId` (`fake-SMS-message-N`, from `GET /receiver-replies/fake/outbound`) and `MessageStatus=undelivered`. Expect `{ ok: true, processed: 1 }`, the attempt `FAILED` with `failureReason: twilio_status_undelivered`, one `check_in.attempt_failed` audit row, the next pending attempt's `scheduledAt` moved to now, and the next `POST /operations/check-ins/run` sending it. Post the same body again: `processed: 0`, still one `provider_webhook_events` row and one `provider_webhook_event_keys` row for `twilio / messaging_status / <sid>:undelivered`.
- Sender name (CB-010): sign in with a Supabase user whose `user_metadata.full_name` is set (or set it in the Supabase dashboard) and call `POST /auth/sync-user`; the next check-in body reads `Hi Margaret, Sam is checking in on you today…` and the backup alert names Sam. Without a name both read as before.
- To see another language, create the receiver with `language: "ar"` (or any seeded code): the next check-in body is Arabic with the personal note in it and `renderFallback: false`. To override copy, `UPDATE channel_templates SET "bodyText" = …` for the `(templateKey, language, channel)` — the row already wins over the in-code copy.

## Invariants — do not break

- Business logic talks to `ChannelRouterService` / `ChannelProvider` only. No module outside `modules/channels/` may import a Twilio symbol or construct a provider.
- `createChannelProviders` is the single switch on `config.channelProviderMode`. Both branches must return one provider per `Channel`, or `ChannelRouterService.providerFor` throws at send time.
- The fake reply controller must stay registered from `channelProviderModeFromEnv()` at module-build time (Nest cannot remove a controller after boot) and must keep the cron-secret bearer on both routes. Both halves are CB-001; `app.module.spec.ts` asserts both routes are absent in configured mode and that the providers, the recorder and the controller share one `FakeOutboundRecorder` instance.
- Only `FakeChannelProvider` may write to `FakeOutboundRecorder`. It holds phone numbers and message bodies in memory by design; a configured provider writing to it would copy real PII into a listable buffer.
- Webhook secret and Twilio signature comparisons stay timing-safe and fail closed on a missing header, missing token or missing `PUBLIC_API_BASE_URL`. The signed URL must be exactly `${PUBLIC_API_BASE_URL}${path}`, so changing a route path or the base URL breaks every signature.
- Twilio inbound messages and delivery statuses are stored **after** successful processing, keyed `(provider, eventType, providerEventId)`, so a transient failure leaves nothing behind and Twilio's retry is processed rather than mistaken for a replay (CB-015).
- Every store of an event that carries a `providerEventId` goes through `createEventIfAbsent`, which claims the key in `provider_webhook_event_keys` (composite primary key = the unique index) inside the same transaction as the `provider_webhook_events` insert (CB-016). `provider_webhook_events` itself is partitioned by `createdAt` in production and PostgreSQL refuses a unique index there that omits the partition key — do not try to put the index back on the events table, and do not bypass the key table with `createEvent` for anything replayable.
- `provider_webhook_events.payload` stays PII-free — inbound messaging: `MessageSid`, `channel`, `bodyLength`, `hasButtonPayload`; delivery status: `MessageSid`, `MessageStatus`, `ErrorCode`, `channel`. Never `To`, `From` or a body.
- `StatusCallback` is only sent when `PUBLIC_API_BASE_URL` is configured, and its path must stay `TWILIO_MESSAGING_STATUS_CALLBACK_PATH` = the controller's signed path, or every status signature fails.
- The sender display name is read at send time and never stored in transcripts or audit metadata; a sender without a name keeps the neutral wording rather than an empty string (the catalog would throw on a blank required variable).
- Rendering fails closed: a missing or blank required variable throws `MissingMessageVariableError`, and a body can never leave with `{{…}}` still in it (`MalformedMessageTemplateError`). Variable values are inserted verbatim and never re-scanned, so a name containing braces cannot inject a placeholder.
- Seed copy contract (`message-catalog.seed.spec.ts` parses the seed migration): every language row keeps the English row's placeholder set and optional sections, keeps `YES`/`HELP`/`STOP`/`REPORT`/`DONE` in Latin letters, has no emoji, and renders to ≤ 320 characters with every optional section filled. Corrections after native review go in a new migration (`UPDATE … SET "bodyText", "approvedAt"`), never by editing the seed file — the seed is `ON CONFLICT DO NOTHING` and would not re-apply anyway.
- Language codes are stored as `varchar(8)` and looked up trimmed and lower-cased; never reintroduce `char(n)` for a code column — `char` pads to width and the padding leaks into API responses and into `templateKey:language` keys (CB-075).
- `ChannelSendResult.rendering` is present only when the provider rendered the body (SMS, fake) and absent for provider-side templates (WhatsApp Content SIDs); `renderingAuditMetadata` must keep tolerating `undefined`.
- Phones are decrypted only at the moment of the provider call, never earlier and never into an audit row.
- `WhatsappProvider.isAvailableForNumber` asserts configuration and therefore throws when credentials are absent; `resolveReachablePlan` catches that and returns `MANUAL_REQUIRED` rather than silently dropping the channel.
- `VoiceProvider` honours `options.fromNumber` (the sticky caller-ID pool) and falls back to `TWILIO_VOICE_FROM_NUMBER`.

## Known gaps

- The eight-language seed is unreviewed by native speakers (`docs/handoffs/message-copy-review.md`); a sender display name longer than 80 characters is truncated, and the `≤ 320 characters` seed contract assumes names of ordinary length.
- CB-019 — Twilio error `code`/`message` are discarded by `twilio-http-client.ts` on a failed send (a delivery failure's `ErrorCode` does reach `check_in.attempt_failed` metadata as `providerErrorCode`, CB-016); dead `SMS_PROVIDER_*` config and the internal `/provider-webhooks/sms` route should go; the inbound URL is undocumented.
- CB-020 — the 8 templates × languages are unapproved by Meta; `TWILIO_WHATSAPP_CONTENT_SIDS` is parsed lazily instead of at boot; `docs/providers/whatsapp.md` does not exist. The `char(5)` padding that broke the `templateKey:language` lookup is gone (CB-075).
- CB-021 — the Meta WhatsApp Cloud API path is half-built: env parsed, no client, no `hub.challenge` GET, custom header instead of `X-Hub-Signature-256`.
- CB-022 — `/twilio/voice` answers JSON where Twilio expects `text/xml` (Twilio 12100); digit `9`/"stop" unmapped; no hosted audio at `VOICE_AUDIO_BASE_URL`; only 5 language folders in `languagePath`; `voice_caller_id_pool` has no writer; dead `VOICE_PROVIDER_*` config.
- CB-046 — no timeout on the Twilio fetch, so a stalled socket can hang an attempt.
- CB-047 — no logging anywhere; Twilio error codes reach audit metadata only for delivery failures, never `attempt.failureReason` or a failed send.
