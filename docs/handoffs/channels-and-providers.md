## What it does

- Every outbound message and call goes through one vendor-neutral `ChannelProvider` (`sendMessage`, `makeVoiceCall`, `isAvailableForNumber`) per `Channel` (`WHATSAPP`, `SMS`, `VOICE`), so cascade, consent and escalation logic never names a vendor.
- `CHANNEL_PROVIDER_MODE` decides the implementations at boot: `fake` yields three `FakeChannelProvider`s that record sends in memory; `configured` yields the Twilio-backed `WhatsappProvider`, `SmsProvider` and `VoiceProvider`.
- `MessageCatalogService` turns a template key + language + variables into the text a person reads: an active `channel_templates` row wins (seeded for en, ar, es, hi, ur, ml, ta, bn on SMS and WhatsApp), then in-code English copy, then English with `fallback: true`; a missing or blank required variable throws. The neutral sender wording ("your family member" / "their family member") is swapped for the phrase of the language actually rendered, so English never lands inside another language's body (CB-079).
- WhatsApp sends an approved Twilio Content Template: the provider picks the most specific template variant whose optional variables are present, numbers the placeholders from that template's own text (`{{1}}`, `{{2}}` by first appearance, Meta's rule) and sends `ContentSid` + numbered `ContentVariables` (CB-020).
- Voice plays hosted WAV prompts inside a one-digit `<Gather>`; the keypress comes back to the Gather action, which maps `1`/`2`/`9` to `YES`/`HELP`/`STOP` and answers TwiML with a spoken thank-you in the receiver's language (CB-022).
- `ChannelRouterService` dispatches by channel and resolves a reachable plan for a phone number (`PRIMARY_AVAILABLE` / `FALLBACK_SELECTED` / `MANUAL_REQUIRED`); the tech profile decides the cascade shape upstream in `CheckInsService`.
- Signed Twilio webhooks bring inbound replies (SMS/WhatsApp text and quick-reply buttons, voice DTMF), message delivery statuses and call outcomes back into `ReceiverReplyService` and `CheckInsService`; every event with an id is stored once (`provider_webhook_event_keys`), so a retry answers `processed: 0` (CB-015, CB-016). A failed Twilio REST call throws `TwilioRequestError` with the Twilio error code (CB-019).
- In fake mode only, `POST /receiver-replies/fake` drives the real reply pipeline with no provider involved, and `GET /receiver-replies/fake/outbound` lists what the fake providers sent; every fake send also prints a `[fake-provider]` line in the terminal.

Every `TWILIO_*` var is `optional()` in the schema, so a `configured` boot with none of them set succeeds and each provider throws `ChannelProviderConfigurationError` at first use. `TWILIO_WHATSAPP_CONTENT_SIDS` is parsed once in the config constructor: malformed JSON fails boot in either mode with a message naming the variable (CB-020). `PUBLIC_API_BASE_URL` also decides whether SMS and WhatsApp sends carry `StatusCallback=${PUBLIC_API_BASE_URL}/provider-webhooks/twilio/messaging/status`: without it no callback is requested. `SMS_PROVIDER_*`, `VOICE_PROVIDER_*`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` and `CHANNEL_WEBHOOK_SECRET` no longer exist (CB-019, CB-021, CB-022); zod strips unknown keys, so a stale value in a `.env` is ignored. `SUPABASE_SERVICE_ROLE_KEY` is optional and never read (CB-025).

## Routes and contracts

- `POST /provider-webhooks/twilio/messaging` — Twilio's inbound URL for the SMS number and the WhatsApp sender (`docs/providers/twilio.md` §2). `X-Twilio-Signature` (HMAC-SHA1 over `${PUBLIC_API_BASE_URL}` + path + sorted key/value pairs, compared timing-safe). Body `From`, `Body`, `ButtonText`, `ButtonPayload`, `MessageSid`; `ButtonPayload` wins, then `ButtonText`, then `Body`. `whatsapp:` prefix on `From` selects `WHATSAPP`. Replays of a stored `MessageSid` short-circuit to `{ ok: true, processed: 0 }`.
- `POST /provider-webhooks/twilio/messaging/status` — the `StatusCallback` of every SMS and WhatsApp send (CB-016). Signed. Body `MessageSid`, `MessageStatus` (`queued`, `sent`, `delivered`, `read`, `undelivered`, `failed`), `ErrorCode`, `To`, `From`. Keyed `messaging_status` / `MessageSid:MessageStatus`, stored once after `CheckInsService.recordMessagingProviderStatus` succeeded; only `undelivered` and `failed` change anything.
- `POST /provider-webhooks/twilio/voice?lang=<xx>` — the `<Gather>` action URL (CB-022). Signed over the full URL, query string included. `Digits` is mapped by `twilioVoiceReplyKeyword` (`1` YES, `2` HELP, `9` STOP; other digits are not handed on; a `SpeechResult` is passed through trimmed); `To` is the receiver's number; `CallSid` becomes the provider message id. Answers `200 text/xml`: `<Response><Say language voice>…</Say><Hangup/></Response>` in the language of `lang` (one of the eight audio languages, English otherwise), for every keypress, mapped or not.
- `POST /provider-webhooks/twilio/voice/status` — `StatusCallback`. Signed. Stores a `voice_status` event (keyed `CallSid:CallStatus`, once) and calls `CheckInsService.recordVoiceProviderFailure({ providerMessageId, providerStatus })`; a replay is `processed: 0` but still runs the guarded transition.
- `POST /provider-webhooks/twilio/voice/amd` — `AsyncAmdStatusCallback`. Signed. Stores a `voice_amd` event (keyed `CallSid:AnsweredBy`, once) and calls `recordVoiceProviderFailure({ providerMessageId, answeredBy })`.
- All webhook routes are `@SkipThrottle()`; the JSON ones answer `{ ok: true, processed: number }` only — never phones, bodies or payloads.
- `POST /receiver-replies/fake` — registered **only** when `channelProviderModeFromEnv() === 'fake'` (`ReceiverRepliesModule.register`); 404 in configured mode. Header `Authorization: Bearer <OPERATIONS_CRON_SECRET>` via `assertBearerSecret`, else 401. Body `{ fromPhone, channel, body, providerMessageId? }`. Returns `{ ok: true, receiverId, action, consentStatus?, checkInId?, checkInStatus?, backupContactId? }`.
- `GET /receiver-replies/fake/outbound?limit=N` — same registration rule and the same cron-secret bearer. Returns `{ ok: true, count, sends[] }`, newest first; `limit` is 1–200 (default 50, 400 otherwise). A record is `kind: "message"` (`to`, `providerMessageId`, `templateKey`, `language`, `fallback`, rendered `body`) or `kind: "voice_call"` (`to`, `providerCallId`, `scriptKey`, `language`, `variables`, `fromNumber?`). Backed by `FakeOutboundRecorder` (200-record ring buffer, one per process), which also prints each record through the Nest logger as `[fake-provider] SMS message to ***3401 (checkin_daily, en) fake-SMS-message-1: "…"`. Configured providers never write to it.

Outbound Twilio shapes (asserted by `configured-channel-providers.spec.ts`): SMS `POST .../Accounts/{Sid}/Messages.json` with `To`/`From`/`Body` (body rendered by the catalog) plus `StatusCallback` when `PUBLIC_API_BASE_URL` is set. WhatsApp the same URL with `whatsapp:`-prefixed `To`/`From`, `ContentSid`, `ContentVariables` (`{"1": …, "2": …}` numbered by first appearance in the chosen template's text) and the same optional `StatusCallback` — the SID comes from `TWILIO_WHATSAPP_CONTENT_SIDS` keyed `templateKey[+optionalSection…]:language` (receiver language, then base language, then `en`, then the language-less key as the English default); a miss throws before any HTTP call. Voice `POST .../Accounts/{Sid}/Calls.json` with inline `Twiml`, `MachineDetection=Enable`, `AsyncAmd=true`, `AsyncAmdStatusCallback`, `AsyncAmdStatusCallbackMethod=POST`, `StatusCallback`, `StatusCallbackEvent='initiated ringing answered completed'`, `StatusCallbackMethod=POST`. The TwiML is two identical `<Gather input="dtmf" numDigits="1" timeout="10" method="POST" action=".../provider-webhooks/twilio/voice?lang={xx}">` blocks each wrapping `<Play>${VOICE_AUDIO_BASE_URL}/{en|ar|es|hi|ur|ml|ta|bn}/{scriptKey}.wav</Play>`, then `<Hangup/>`. A non-2xx Twilio answer is a `TwilioRequestError` (`code`, `status`, `moreInfo`, `failureReason` = `twilio_<code>` or `twilio_http_<status>`; Twilio's `message` is dropped because it quotes phone numbers).

Message template keys and the variables each requires (`{{var}}` required, `{{#var}}…{{/var}}` optional section):

| Template key                            | Required                                           | Optional                                | Sent by                             |
| --------------------------------------- | -------------------------------------------------- | --------------------------------------- | ----------------------------------- |
| `consent_request`                       | `receiverName`, `senderDisplayName`                | `personalNote`                          | `receiver-consent.service.ts`       |
| `checkin_daily`                         | `receiverName`, `senderDisplayName`                | `personalNote`                          | `check-ins.service.ts`              |
| `checkin_retry`                         | `receiverName`, `senderDisplayName`                | `personalNote`                          | `check-ins.service.ts` (attempt 2+) |
| `receiver_checkins_paused`              | `receiverName`, `senderDisplayName`                | —                                       | `receivers.service.ts`              |
| `receiver_checkins_ended`               | `receiverName`, `senderDisplayName`                | —                                       | `receivers.service.ts`, `receiver-reply.service.ts` (STOP) |
| `account_step_up_otp`                   | `code`, `validityMinutes`                          | —                                       | `account/step-up.service.ts` (SMS only) |
| `backup_contact_missed_checkin_alert`   | `contactName`, `receiverName`, `senderDisplayName` | `channelsTried`, `locationInstructions` | `escalations.service.ts`            |
| `backup_contact_help_alert`             | `contactName`, `receiverName`, `senderDisplayName` | `channelsTried`, `locationInstructions` | `escalations.service.ts`            |
| `backup_contact_sender_requested_alert` | `contactName`, `receiverName`, `senderDisplayName` | `channelsTried`, `locationInstructions` | `escalations.service.ts`            |

`senderDisplayName` is filled the same way by every caller: `UsersService.senderDisplayNameFor(userId, fallback?)` decrypts `users.displayNameEncrypted` and returns `NEUTRAL_SENDER_DISPLAY_NAME` ("your family member") when the sender has no name; `escalations.service.ts` passes `NEUTRAL_SENDER_DISPLAY_NAME_FOR_BACKUP_CONTACTS` ("their family member"). The catalog (SMS, fake) and the WhatsApp provider replace either constant with `NEUTRAL_SENDER_DISPLAY_NAMES_BY_LANGUAGE[language]` for the language actually sent (CB-079; machine translations, see the copy-review tracker). The name is decrypted for the provider call only and never written to an audit row.

Voice uses `scriptKey`, not the catalog: `TWILIO_VOICE_SCRIPT_KEYS` = `checkin_daily_voice` (every attempt, no retry variant), `consent_request_voice`, `receiver_checkins_paused_voice`, `receiver_checkins_ended_voice` (also the STOP confirmation), `sender_escalation_siren_voice` (sender, English only). The recordings are generic (no names), which is why voice calls carry `variables: {}`. What each must say, the audio layout and the keypad are in `docs/providers/twilio.md` §4.

Languages: `channel_templates` holds every key above for `en`, `ar`, `es`, `hi`, `ur`, `ml`, `ta`, `bn` on `SMS` and `WHATSAPP`. Any other language falls back to English with `renderFallback: true` in the audit metadata. Every non-English body is a machine translation with `approvedAt` NULL. `{{channelsTried}}` is still filled in English by `describeChannelsTried`.

## How to exercise it locally (fake mode)

- Set `CHANNEL_PROVIDER_MODE=fake` and `OPERATIONS_CRON_SECRET` in `apps/backend/.env` per `docs/EMULATOR_RUNBOOK.md` §3, then start the backend. No `TWILIO_*` value is needed.
- Drive an inbound reply: `POST /receiver-replies/fake` with `Authorization: Bearer <OPERATIONS_CRON_SECRET>` and `{"fromPhone":"+44...","channel":"SMS","body":"YES"}`. Without the bearer it is 401; with `CHANNEL_PROVIDER_MODE=configured` the route is 404.
- Drive an outbound send: `POST /operations/check-ins/run` (cron-secret bearer). The `check_in.sent` audit row carries `renderedLanguage` and `renderFallback`; the rendered body prints in the backend terminal as a `[fake-provider]` line and is returned by `GET /receiver-replies/fake/outbound` (cron-secret bearer).
- Exercise a Twilio route locally by setting `TWILIO_AUTH_TOKEN` and `PUBLIC_API_BASE_URL` to test values and computing the HMAC-SHA1 signature the way `docs/providers/twilio.md` §6 shows; an unsigned request is 401. A signed `POST /provider-webhooks/twilio/voice?lang=ar` with `Digits=1` answers `200 text/xml` with an Arabic `<Say>`; `Digits=9` revokes consent.
- Delivery status (CB-016): drive `POST /provider-webhooks/twilio/messaging/status` yourself with a signed body whose `MessageSid` is a SENT attempt's `providerMessageId` and `MessageStatus=undelivered`; expect the attempt `FAILED` with `failureReason: twilio_status_undelivered` and a replay answering `processed: 0`.
- Sender name (CB-010, CB-079): with `user_metadata.full_name` set and `POST /auth/sync-user` called, the next check-in body and the STOP confirmation name the sender; without a name a receiver created with `language: "ar"` gets the Arabic neutral phrase, never "your family member".
- Voice audio and caller IDs: `npm --prefix apps/backend run providers:check-voice-audio -- --base-url=… --languages=en` and `npm --prefix apps/backend run db:seed-caller-ids -- --numbers=… --dry-run` (`docs/providers/twilio.md` §4–§5).

## Invariants — do not break

- Business logic talks to `ChannelRouterService` / `ChannelProvider` only. No module outside `modules/channels/` may import a Twilio symbol or construct a provider; the provider-webhooks controller is the one adapter that reads Twilio's request shapes and it imports only `twilio-rendering` helpers.
- `createChannelProviders` is the single switch on `config.channelProviderMode`. Both branches must return one provider per `Channel`, or `ChannelRouterService.providerFor` throws at send time.
- The fake reply controller must stay registered from `channelProviderModeFromEnv()` at module-build time and must keep the cron-secret bearer on both routes (CB-001); `app.module.spec.ts` asserts both routes are absent in configured mode, that the providers, the recorder and the controller share one `FakeOutboundRecorder`, and that `ReceiverReplyService` receives `UsersService`.
- Only `FakeChannelProvider` may write to `FakeOutboundRecorder`. It holds phone numbers and message bodies in memory by design.
- Twilio signature comparisons stay timing-safe and fail closed on a missing header, missing token or missing `PUBLIC_API_BASE_URL`. The signed URL must be exactly `${PUBLIC_API_BASE_URL}${path}` plus the query string as received, so changing a route path, the base URL or the `lang` parameter breaks every signature.
- The voice Gather action must answer `200 text/xml` TwiML, whatever happened (an unmapped digit included); a JSON body there is Twilio error 12100 and an error tone for the receiver. Digit-to-keyword mapping lives in `twilio-voice-input.ts`, never in `ReceiverReplyService`.
- Twilio inbound messages and delivery statuses are stored **after** successful processing, keyed `(provider, eventType, providerEventId)` through `createEventIfAbsent`, so a transient failure leaves nothing behind and Twilio's retry is processed rather than mistaken for a replay (CB-015, CB-016). `provider_webhook_events` is partitioned by `createdAt` in production; never put the unique index back on it or bypass the key table for anything replayable.
- `provider_webhook_events.payload` stays PII-free — inbound messaging: `MessageSid`, `channel`, `bodyLength`, `hasButtonPayload`; delivery status: `MessageSid`, `MessageStatus`, `ErrorCode`, `channel`. Never `To`, `From` or a body. `TwilioRequestError.message` never carries Twilio's `message` for the same reason.
- `StatusCallback` is only sent when `PUBLIC_API_BASE_URL` is configured, and its path must stay `TWILIO_MESSAGING_STATUS_CALLBACK_PATH` = the controller's signed path.
- WhatsApp placeholders are numbered from the `channel_templates` WHATSAPP row (or in-code English) for the language and variant actually sent, by first appearance; `docs/providers/whatsapp.md` is generated from the same rows with the same helper. Changing a row's word order changes its numbering, which means a new Meta template. A required variable that is blank throws before the HTTP call; an optional value with no approved variant is dropped, never sent empty.
- The sender display name is read at send time and never stored in transcripts or audit metadata; a sender without a name keeps the neutral wording in the language of the copy (catalog for SMS/fake, provider for WhatsApp), never an empty string or English inside another language.
- Rendering fails closed: a missing or blank required variable throws `MissingMessageVariableError`, and a body can never leave with `{{…}}` still in it. Variable values are inserted verbatim and never re-scanned.
- Seed copy contract (`message-catalog.seed.spec.ts`): every language row keeps the English row's placeholder set and optional sections, keeps `YES`/`HELP`/`STOP`/`REPORT`/`DONE` in Latin letters, has no emoji, renders to ≤ 320 characters with every optional section filled, and never shows the English neutral phrase. Corrections after native review go in a new migration, never by editing the seed.
- Language codes are stored as `varchar(8)` and looked up trimmed and lower-cased; never reintroduce `char(n)` for a code column (CB-075).
- `ChannelSendResult.rendering` reports the language actually sent: rendered body language for SMS and fake, approved template language for WhatsApp (with `fallback: true` when the English template stood in); `renderingAuditMetadata` must keep tolerating `undefined`.
- Phones are decrypted only at the moment of the provider call, never earlier and never into an audit row.
- `WhatsappProvider.isAvailableForNumber` asserts configuration and therefore throws when credentials are absent; `resolveReachablePlan` catches that and returns `MANUAL_REQUIRED` rather than silently dropping the channel.
- `VoiceProvider` honours `options.fromNumber` (the sticky caller-ID pool) and falls back to `TWILIO_VOICE_FROM_NUMBER`. `TWILIO_VOICE_SCRIPT_KEYS` must list every `*_voice` key a caller uses (`twilio-rendering.spec.ts` scans them) and `check-voice-audio.mjs` must carry the same list.

## Known gaps

- CB-022 — the code half is done; the recordings, their hosting at `VOICE_AUDIO_BASE_URL` and the native review of the prompt scripts and the `<Say>` sentences wait on decision 3. Until then a configured-mode call fails at `<Play>`. No digit maps to REPORT. Urdu has no Twilio voice: the thank-you is Hindustani in Devanagari read by the Hindi voice (a decision the founder can flip in `TWILIO_VOICE_REPLY_SAY`).
- WhatsApp — no template is created or approved yet (`docs/providers/whatsapp.md` is the work list); the eight-language seed is unreviewed; the Arabic check-ins mention the sender twice (one number reused), which Meta may reject; quick-reply limits assumed ≤ 3 buttons; Meta's newer named parameters are not used.
- CB-047 — `TwilioRequestError.failureReason` exists but `check-ins.service.ts` still records `PROVIDER_SEND_FAILED` on a failed send and nothing is logged.
- CB-046 — no timeout on the Twilio fetch, so a stalled socket can hang an attempt.
- A sender display name longer than 80 characters is truncated, and the `≤ 320 characters` seed contract assumes names of ordinary length; `{{channelsTried}}` is English in every language.
